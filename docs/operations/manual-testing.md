## Maintenance And Policy Checks

1. Open Settings with no configured policy: both numerical inputs are blank, with no invented concentration or tactical default. Missing/zero/negative/over-100 position, negative/over-100 tactical, malformed numbers and missing acknowledgement reject without writes. Blank tactical is accepted as null; zero tactical is an explicit limit, not an inferred default.
2. Submit explicit limits against a confirmed revision. Check the new current revision, incremented policy version and pending run pinned to it; ledger, instruments, independent snapshot/reconciliation and previous run inputs are unchanged. Resubmit the old revision or submit an import preview based on it: reject as stale. Previously confirmed-preview replay returns its original revision, not the new policy. Suitability/sized BUY/REDUCE/SELL remain blocked without required scenario inputs; policy save is not implementation of sizing or trade authorization.
3. Follow Settings -> Maintenance. Anonymous/wrong identity requests must reject before storage access; POST export/delete/policy without antiforgery rejects. GET must not export or delete. Export requires scope/rights acknowledgement and matching current revision. Verify no-store and JSON attachment, current portfolio plus complete embedded run evidence/tasks/briefs/usage, up to 100 latest runs, and truncation warning at that boundary. Originals/report/stage bytes and older unpinned revisions are not included; verify existing individual original/report links. An export over 8 MiB rejects with 413 and no attachment; obtain older/larger history through an authorized administrator before purge. Do not infer application restore from JSON availability.
4. Before deletion, cancel work through Runs, let workers settle, stop scheduled/on-demand worker processes and pause other imports/submissions. A Running claim, even expired or cancel-requested, must reject deletion. Confirm an old Running row beyond the latest 100 still blocks in SQL. Do not forcibly treat expired rows as safe; arrange normal cancellation/recovery/settlement while workers are permitted to run, then stop processes. The page does not enforce shutdown or an atomic maintenance fence, so deletion while concurrent workers/submissions remain is unsupported, not a passed race-safety check.
5. On an isolated disposable workspace, reject stale revision, omitted loss/shutdown acknowledgements and wrong `DELETE WORKSPACE` text with no deletion. With settled workers/exclusive access and correct acknowledgement, check actual SQL removal of all previews/ledger identities/revisions/runs and current pointer reset. Check monotonic revision counter, monthly AI reservations/totals, source-credit entries and cookie-key ring survive. Check current workspace-prefix blobs are removed; versions/soft-delete/backups/copies are not claimed erased.
6. Inject an artifact failure after SQL deletion using test-only transports: response explicitly says partial deletion (503), SQL investment rows stay deleted, artifact remainder persists, sensitive exception details are not shown. Keep exclusivity, retry from revision 0 and verify artifact cleanup completes. With current-blob count/time bounds, repeat explicit cleanup rather than reporting complete after an exception. Disconnect/reload cannot recover a durable receipt; reconcile the empty SQL state and repeat cleanup before reimporting.
7. For source rights expiry/withdrawal, record **Blocked** for selective per-vendor/per-run and automatic expiry. Full-workspace purge is the coarse application remedy, not a proven vendor-only cascade. Review versions, soft-delete, backups and exported copies with a storage administrator. No immediate erasure, preserved reproducibility or restore guarantee; cloud backup/retention verification is NotRun without its authorized environment.
