# Security And Retention

## Identity And Permission Matrix

| Identity | Intended rights | Explicit exclusions |
| --- | --- | --- |
| Authorized user | Entra tenant/object allowlisted private web routes/actions/downloads | Other tenant/object, arbitrary trusted identity headers, broker execution |
| Web UAMI | SQL seven-table DML; Blob Contributor at documents and key container; ACR Pull; optional existing auth vault secret GET | ARM job start/modify, worker AI/provider secrets, inference grant, db_owner/schema DDL |
| Worker UAMI | SQL seven-table DML; document-container Blob Contributor; ACR Pull; scoped OpenAI User on selected existing/new account; optional provider vault secret GET | Cookie-key container, HTTP ingress, ledger/policy model tools, ARM deployment, broker tools |
| External WIF deploy principal | Explicit authorized resource-group changes and identity assignment; separately authorized role assignment scopes; optional ACR Push | Runtime reuse; automatically inferred SQL admin or subscription-wide Owner |
| Separate SQL bootstrap/migration principal | Reviewed initial DDL; manually approved user/grant bootstrap via supplied federated Entra administrator | Granting persistent DDL/db_owner to web/worker; unaudited automatic migration |

ARM permissions and SQL permissions are different. Provisioning role assignments can require User Access Administrator or a narrow custom role; scope external authority to the actual RG/account/container boundaries, including a separate existing Foundry RG where used. Never solve propagation/auth failures by widening runtime grants.

Web uses Microsoft.Identity.Web, Entra credential, explicit allowed host and tenant/object checks; authenticated tenant membership alone is insufficient. Cookie/antiforgery, no-store, safe rendering/CSP and size/rate handling need deployed/manual verification. Local Development identity is loopback-only, rejects forwarded/proxy indicators and is forbidden in production. Production configuration missing auth/keys fails closed.

ACA terminates TLS and forwards HTTP internally. Bicep config enables forwarded headers and explicit HTTPS port for ASP.NET redirects; ingress denies insecure HTTP. Broad framework forwarded-header opt-in is acceptable only behind the reviewed ACA ingress with no alternate direct listener path; test forged forwarded host/scheme handling and actual allowed-host filtering before acceptance. No application-level unauthenticated health URL is assumed.

Managed identity authenticates SQL/Blob/inference; Basic ACR private authenticated pull has admin user off. Private containers mean no anonymous access, not network-private endpoints. Storage shared-key auth is disabled in production. No keys/SAS/auth secrets in outputs, source, image layers, build context, logs, URLs, report text or model context. Optional existing-vault references require explicit identity GET access and rotation review; no vault is purchased here.

Worker-only retrieved text is untrusted data. Approved HTTPS hosts/path/IP limits, redirect/DNS/SSRF defenses, bounded bytes/time, role tool allowlists, strict schemas and deterministic evidence/policy gates limit influence. Prompts/critic are not the security boundary. Models cannot execute SQL/shell/trades, deploy, publish directly or modify ledger/policy. Raw statements never go to models. Input minimization and rights-valid evidence matter even when statements are private.

## Retention And Maintenance

Originals are retained privately until explicit authorized deletion, not a silent lifecycle age rule. Bicep enables Blob versioning and seven-day blob/container soft-delete; SQL short-term backup retention is seven days; Log Analytics defaults 30 days, configurable 30..90, with a 0.1-GB/day quota. No automatic document lifecycle purge, SQL LTR, geo/zone HA, archive tier or duplicate telemetry sink is enabled. Versioning creates storage growth; soft-delete windows are not expiry of all previous versions.

Only sanitized operational identifiers/status/errors are appropriate in logs. Daily ingestion quota/retention limit bytes, not a hard monetary cap, and may suppress useful telemetry after exhaustion. SQL durable run/stage/usage status is the history path; do not log full model messages/evidence/CSV or enable sensitive SDK tracing. No continuous availability probe/keepalive that prevents web scale-to-zero.

### Private Maintenance And Export

Settings links to `/Maintenance`. All maintenance and policy routes inherit the global authenticated tenant/object allowlist; POST export, deletion and policy forms require antiforgery. Export and deletion require explicit acknowledgements and a bound portfolio revision; deletion also requires the exact `DELETE WORKSPACE` confirmation. Invalid/stale submissions are rejected with fixed messages, not exception details or source text in logs.

JSON export contains the current immutable portfolio plus up to the latest 100 stored AnalysisRuns, including each run's pinned portfolio, complete embedded evidence, tasks, briefs, trace and usage. It is capped at 8 MiB during serialization; oversized exports return 413 without a partial download. A manifest records the scope and `HistoryMayBeTruncated` when the 100-run boundary is reached. This is **not complete all-time history** or a restore package. Older runs, unreferenced historical revisions, previews, original file bytes and referenced report/stage artifact bodies are excluded. Available originals and reports retain their existing individual authenticated download routes. Arrange a reviewed administrator export for older/larger history before deletion. Downloads are private attachments with no-store; the user must separately handle copies and licensed retention/withdrawal obligations. Run records are read snapshots, not an atomic database-wide export under simultaneous worker updates.

Full-workspace deletion calls the existing serializable `DeletePortfolioAsync` and then artifact `DeleteAllAsync`. The SQL operation removes previews, ledger identities, all revisions and all runs, resetting only the current portfolio pointer. AI monthly totals/reservations, source-credit accounting and the monotonic last-revision counter survive; Blob cookie-key XML is outside document cleanup. Artifact cleanup processes current document-prefix blobs with the existing 10,000-count/two-minute bound, not all retained versions/soft-deleted data. An artifact exception, including timeout/cancellation after SQL deletion, produces an explicit `SqlDataDeletedArtifactsPending` response (503). Keep maintenance exclusive and repeat deletion from the now-empty revision to finish cleanup; do not reimport before retry. A failed SQL call does not start artifact deletion; reload and reconcile SQL state before retrying an uncertain operation. There is no distributed SQL/Blob transaction or durable partial-cleanup receipt; after disconnect or reload, repeat explicit cleanup while exclusivity remains in effect.

**Concurrency prerequisite and remaining gap:** cancel relevant work through Runs, wait for worker settlement, stop scheduled and on-demand worker processes and pause other imports/submissions for the entire SQL-plus-Blob cleanup. The form requires an explicit acknowledgement of that exclusive maintenance window. The production page checks SQL for **any** Running row, including expired/cancel-requested claims, without the 100-run UI limit. Such rows refuse deletion; cancellation alone is not terminal settlement. However, this check is not inside the unchanged SQL deletion transaction, and the page cannot enforce worker shutdown or pause other clients. A new claim/submission or previously issued worker I/O can race cleanup if the prerequisite is violated. Concurrent-worker deletion is therefore **not verified safe**; an atomic maintenance fence/claim guard requires a separate authorized store/worker change. The page does not stop or restart workers itself.

### Licensed Withdrawal And Expiry

Selective per-provider/per-run withdrawal, automatic finite licensed-data expiry and dependent tombstone-only invalidation remain **Blocked / not implemented**. Licensed material can be embedded across run evidence/tasks/briefs and report/stage blobs; deleting an individual source blob is not sufficient. The available application remedy is an explicitly authorized full-workspace purge under the exclusive maintenance prerequisite, followed by administrator review of versions, soft-delete, SQL backups and any exported copies. Do not enable finite-retention licensed evidence on the assumption that this page automatically enforces its expiry. Retention rights override historical replay wishes; deletion reduces or removes audit/reconstruction ability and does not imply restoration support.

### Explicit Risk Policy

Settings accepts a required explicit maximum-position percentage greater than 0 and at most 100, and an optional tactical percentage from 0 to 100. No numeric defaults are supplied; blank tactical remains null. Acknowledged saves atomically check the expected current revision under serializable SQL isolation, persist an immutable new portfolio revision with incremented policy version, copy the ledger/instruments/snapshot/reconciliation unchanged, and enqueue pending work pinned to that revision. Previously confirmed previews and historical runs retain their original input/policy. The default interface method throws for stores without this capability; production SQL implements it. Configuration is informational and does not implement sizing, prove suitability or bypass missing scenario/valuation/eligibility inputs. No reset-to-unconfigured command is supplied by this method.

Administrator follow-up: inventory active run/revision/artifact/version references and reservations before purge; revoke/stop relevant processing; use full-workspace purge where selective withdrawal is unavailable; enumerate/purge approved document versions where allowed; document SQL backup and Blob soft-delete expiry/caveats. Rerun authenticated reads and retain an audit outcome without content/secrets. Previous Blob versions, soft-delete, backup retention and downloaded copies require separate custody review; application success cannot guarantee their erasure or licensed-retention compliance.

Never delete the Data Protection ring as ordinary portfolio cleanup; doing so disrupts sessions/antiforgery/history access and may affect decryptability. Protect key container and backups separately. Source-only deletion, provider termination and full-account purge require agreed retained metadata and backup/legal limits. Originals' perpetual intent cannot override provider copyright/licensed retention.

Test restore with a separate explicitly authorized target, verify schema/collation/identity users, Blob manifest references/version availability and current permissions, then reconcile without overwriting the source. Cloud restore creates charges and needs the same forecast/authority gate. No RPO/RTO, irreversible immediate backup deletion or successful restoration is established by these templates.
