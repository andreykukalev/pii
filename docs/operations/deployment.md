# Deployment And Local Operation

**No Azure login, provisioning, purchases, hosted pipeline run or model/provider calls were performed in this task.** Templates are locally compiled; deploy defaults false. Resolve [readiness blockers](readiness.md), a dated after-tax forecast within USD100, service entitlement and explicit resource authority before any authenticated apply or push. Even infrastructure-only deployment creates charges.

## Independent Stages

The only deployment workflow is [infra/README.md](../../infra/README.md), with subscription RG-only foundation, independent modern Foundry, private storage, SQL data, optional monitoring, compute infrastructure and separate application entrypoints. [The local Azure dependency guide](../../infra/local/README.md) and [exact-key templates](../../infra/parameters/local/appsettings.Development.json) cover developer Entra auth and coordinated host changes. Use the same existing `$manifest` for manual stage WhatIf -> review -> Apply. Every wrapper requires `-ManifestPath`; all nonsecret deployment settings come exclusively from that JSON, including required nonempty-GUID root `subscriptionId` and `shared.auth.tenantId`. No CLI subscription or environment file/subscription selector is supported. The [central placeholder](../../infra/parameters/manifest.json) defines shared identifiers; wrappers never rewrite your selected file. Default `deploy-all` excludes compute/application and skips disabled monitoring. Compute never starts workloads; Foundry account/project provisioning is not model activation, and model deployment defaults OFF.

The [pipeline](../../azure-pipelines.yml) invokes the same selected-stage wrappers and manifest resolver. Each run selects exactly one stage; there is no combined template, flat parameter file or implicit compute/application expansion. Application workloads bind already-created environment/registry/UAMIs and preserve the runtime key schema; worker schedule and workloads default OFF independently. Inventory previously deployed names/grants before transferring ownership to stages; source cleanup never deletes existing resources or data.

Local-only verification: `./infra/validation/Test-ManifestResolution.ps1`, `./infra/validation/Test-ModularStages.ps1`, `./infra/validation/Test-DeploymentWrappers.ps1`, `./infra/validation/Test-LocalIntegrationTemplates.ps1`, `./infra/validation/Test-StagedPipeline.ps1`, and `./infra/scripts/deploy-all.ps1 -ManifestPath ./infra/parameters/manifest.json -Action Validate -Offline` after filling the existing manifest's subscription placeholder. Omit `-Offline` only for independently authorized ARM validation. All Apply actions require `-AuthorizeApply -AcknowledgeCost`; no wrapper logs in/registers providers/starts jobs/builds images/extracts keys/deletes data.

## Existing Databases

`EnsureCreated` creates a new database schema; it **does not migrate** an existing LocalDB or Azure SQL database. The existing local `PiiDevelopment` database was not deleted, recreated or upgraded in this task. `SqlWorkspaceStore` initialization is unchanged and does not auto-detect/add these tables. Missing credit tables produce `TwelveDataSharedCreditStoreUnavailable` before vendor HTTP; fixture and other permitted nonvendor source behavior remains independent.

For an existing workspace, disable discretionary Live calls and drain workers, preserve a reviewed backup/export, then use a separate authorized administrative connection to run [source-credit-upgrade.sql](../../infra/sql/source-credit-upgrade.sql) with the exact `DatabaseName`. The SQLCMD script verifies the target/workspace head, obtains a transaction-owned schema application lock, creates both missing credit tables atomically, rejects a partial schema and does not reset any existing consumption or portfolio/monthly data. It grants the two narrow credit permissions to an existing fixed worker principal; it does not create/rebind identities or grant web access. If both credit tables already exist, it leaves them unchanged; operators must review metadata rather than assume this existence check repairs incompatible schemas. Existing broad grants inherited from outside this repository must be reviewed separately.

For explicit local administrative integration, [SqlSourceCreditStore.AddSchemaAsync](../../src/Pii.Infrastructure/SqlSourceCreditStore.cs) provides the equivalent additive table operation using the chosen `IDbContextFactory<WorkspaceDbContext>`. It is never called by DI, fetch, normal startup or production runtime. It requires DDL authority and does not manage principal grants; use the reviewed SQL script for production upgrades. Do not give runtime identities DDL to make it work. Validate the full resulting schema and worker login before resuming calls. Do not rerun the empty-database bootstrap or drop real data as a migration strategy.

Acceptance scenarios may instead use a **new** dedicated database such as `PiiSourceCreditAcceptance20261011` and an isolated artifact container, shared by web/worker. That allows normal new-schema `EnsureCreated` without modifying the real local ledger. Both web and worker EF models include the credit tables; only worker DI registers the actual credit store. Portfolio deletion intentionally preserves source credit totals/entries as well as monthly USD reservations.

## CI And Rollback

[Pipeline](../../azure-pipelines.yml) pins SDK 10.0.401; Windows job runs whole-solution tests with actual LocalDB, NuGet all/transitive vulnerability gate and limited credential signatures. Linux job compiles Bicep, checks templates, resolves actual SDK/ASP.NET image digests, verifies exact SDK, builds non-root images, records runtimes/local IDs and saves image artifacts. No Node build stage is required by the application; YAML parser tooling is only local syntax validation.

Variables supplied outside source: `AzureServiceConnection` (existing WIF connection), `DeploymentManifestSecureFile` (the SAME central manifest), `DeploymentEnvironment`, `PiiDeploymentAuthority=true`, `PiiAfterTaxForecastApproved=true`. Subscription/RG/registry/location come only from the manifest, not duplicate pipeline variables. Restrict these, secure-file/service-connection permissions and branch policy. Configure environment **approval/checks outside YAML**, disallow self-approval as appropriate, and do not grant automatic pipeline access. These variable names are procedural gates, not verified authority documents. Missing `Pii.slnx` or LocalDB blocks full CI, never silently skips tests. Hosted-agent grant/capacity/LocalDB availability is unverified.

Build never authenticates Azure. `deploy=false` skips WhatIf/Apply. To deploy, explicitly set `deploy=true` and one `deploymentStage` from foundation/foundry/storage/data/monitoring/compute/application; selecting application or compute is never inferred from enabled dependencies. The selected stage must also be enabled in the manifest. Optional `secureParametersSecureFile` selects a protected declared-secure-only file for that stage; default empty skips its download. Linux AzureCLI tasks use PowerShell Core and the same wrappers as Windows PowerShell 5.1 manual operation. The WIF connection must target the manifest subscription and have its separately reviewed required permissions.

Both deployment jobs gate authority, forecast, main branch and non-PR execution. Preview and environment-approved Apply download the same secure files and copy the manifest without modification to the stable `$(Pipeline.Workspace)/pii-config/manifest.json` path. Environment values cannot select a file or override its settings. That stable path preserves manifest-path fingerprints across agents. Temporary copies are removed in `finally`; secure-file task downloads are agent-cleaned. Release artifacts contain stage/module/script/SQL code and image evidence, not deployment configuration. Only per-stage receipts are published to `change-review`, containing nonsecret identifiers, selected manifest path and hashes, never secure values or ARM payloads. Restrict receipt artifact access as resource identifiers are still private operational metadata.

Apply downloads the reviewed receipt and runs the same selected wrapper with both explicit authorization switches. It rejects changed manifest/secure-file/template/path inputs, Delete changes and property-level ARM preview drift before incremental create. Full payloads are hashed in memory, with only resource IDs/change types displayed. Protect secure-file versions and immutable release artifacts, privately review manifest/secret changes, and approve the configured environment only after reviewing the receipt and preview log. No automatic registry push, manifest image substitution, SQL bootstrap or worker start is part of pipeline deployment. Pin already published compatible image digests in the central manifest before preview; changing them requires a fresh preview. Never archive secret-bearing parameter files.

Retain known-good image digests, nonsecret config version, schema compatibility and cookie key ring. Roll back image/config only through reviewed what-if/approval; do not restore SQL blindly over newer confirmed history or delete originals to make rollback fit. Disable new discretionary calls before maintenance; do not reset reservations. Backup restore/export/provider withdrawal and image cleanup need reviewed manual maintenance and tests; no UI export/delete or automatic ACR Basic retention policy is claimed. Keep at least current/rollback digests and remove only approved old unreferenced images.
